  2. How authentication works

  - What the JWT contains: only {"exp", "sub": str(user.id)}, signed with HS256
    and SECRET_KEY (security.py:22-26 (backend/app/core/security.py#L22-L26)).
    It carries no role or superuser claim.
  - Reloaded on every request: yes. get_current_user decodes the token and then
    runs session.get(User, token_data.sub) on every authenticated request
    (deps.py:30-46 (backend/app/api/deps.py#L30-L46)). A role change therefore
    takes effect on the user's next request, with no need to issue a new token
    or log in again.
  - Failure codes:
    - A bad or expired token returns 403 "Could not validate credentials",
      not 401.
    - A missing user returns 404.
    - An inactive user returns 400.
    - A missing Authorization header gets 401 from OAuth2PasswordBearer itself.

  3. How the frontend handles 401/403

  - The global QueryCache and MutationCache onError call handleApiError
    (main.tsx:22-30 (frontend/src/main.tsx#L22-L30)). On 401 or 403 it clears
    access_token from localStorage and does a hard redirect to /login. It treats
    401 and 403 the same way.
  - On top of that, each mutation's own onError calls handleError (utils.ts:17
    (frontend/src/utils.ts#L17)), which shows detail in a toast.
  - This matters for role-based access: a logged-in user who hits a permission
    403 (the "not enough privileges" response) is logged out. That's also how
    the backend's invalid-token 403 gets treated as "logged out". If role-based
    access adds more legitimate 403s, users will be signed out each time unless
    one of these changes:
    - the backend returns 401 for an invalid token and the frontend logs out
      only on 401, or
    - the frontend tells the two cases apart by detail.
  - The admin beforeLoad uses UsersService directly, outside React Query, so its
    errors don't go through handleApiError.
